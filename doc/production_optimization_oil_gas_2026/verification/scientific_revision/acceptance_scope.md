# Scientific revision acceptance scope

The September 2026 execution-checked release is preserved while its scientific revision is prepared. The scope is all 35 chapters, every executable manuscript example, all 35 notebooks, equations and quantitative claims. Exercises without supplied solutions are assignments, not completed calculations. External-system integration patterns require explicit fixtures and cannot establish operation of an unavailable external service.

Three distinct evidence levels are recorded: execution; numerical and physical solution verification (units, conservation, phase equilibrium, domain and constraints, convergence and analytical limits); and model validation against independent reference data. No model is described as universally field-validated merely because it runs or conserves mass.

Acceptance requires every chapter to have a documented scientific read-through and disposition of material findings; every retained executable example to execute from its literal published source; and every numerical engineering example to state its scope, assumptions and appropriate checks. Failed engineering examples must be corrected or replaced with an accepted calculation. Published optimizer optima require explicit success, feasible independent replay and comparison with a sampled search or analytical bound. Transient examples require actual inventory integration, conservation and timestep checks. Distillation requires rigorous convergence and material, equilibrium and energy checks; corrected product flows alone do not qualify.

Independent property benchmarks use separately retained reference values and declared tolerances, not expected values generated by the same NeqSim run. Deterministic mathematical identities use tight numerical tolerances; correlations and EOS predictions use separately justified domain-specific engineering tolerances. A passing benchmark supports its stated domain only.

An explicitly rejected native result may remain as a diagnostic example beside its checked replacement or clearly bounded API discussion. Its successful execution does not make that result an accepted engineering calculation. The final coverage ledger must identify these cases, genuine software-only fragments and external integration patterns separately; no numerical example may be accepted solely because it executes without an exception.

The final release must match the reviewed code hashes, reproduce its figures and numerical text, pass PaperLab evidence checks and PDF/HTML structure/layout checks, and retain an honest list of remaining validation limits. The existing publication is replaced only after review of the exact candidate.

Roles: PaperLab foundations reviewer owns chapters 1–18; optimization reviewer owns chapters 19–32 and 34–35; notebook verifier owns all notebooks and independent benchmarks; root book author/release reviewer owns chapter 33, bibliography integrity, consolidated evidence and publication.

Runtime: explicitly selected bundled Codex Python; Java classes from the current ChatGPT/NeqSim checkout, not the older checkout containing PaperLab. Existing reference files, figures and prior reports are preserved for traceability.
